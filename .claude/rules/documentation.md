# ドキュメントの書き方

## 文書の一覧と役割

| 文書 | 役割 | 変えるとき |
|---|---|---|
| `docs/reference/` | **正本**。使い方・出力・メッセージ・終了コード（`cli.md`）と記録の形式（`history.md`） | 仕様を変えるとき。**先に文書、後で実装**。見え方が変わるなら人間の了承が先（`.claude/rules/working-with-human.md` 4章） |
| `docs/design/` | 開発に加わる人向け：`overview.md`（目的・やらないこと）・`decisions.md`（判断と理由）・`limitations.md`（制限と追加の候補） | 判断が変わったとき。候補を採用したら `limitations.md` から消し、`reference/` に書く |
| `docs/examples/` | 実際の入出力。`internal/docs` のテストが実装との一致を確かめる | 挙動を変えたとき（テストが落ちる） |
| `dev/` | 開発のうちうち：`roadmap.md`（段階）、`review/`（了承をもらう資料） | 段階が進んだとき |
| `README.md` | 利用者向けの入口（入れ方、使い方の要点、`docs/` への案内） | 使い方が変わったとき |
| `CLAUDE.md`・`.claude/rules/` | 開発のルール | 気づき・落とし穴が見つかったとき |

- `docs/` から `dev/` を参照しない（`docs/` は利用者にも見せる）
- 進捗・決定・質問は文書ではなく **mtqg** に記録する（`.claude/rules/mtqg-usage.md`）

## 仕様と実装がずれたとき

- **`docs/` が正本。** 実装を `docs/` に合わせる
- `docs/` 自体に誤りや矛盾を見つけたら、黙って実装に合わせない。重要な判断として、推奨案つきで聞く
- 仕様を直すと決まったら、**同じ変更の中で** `reference/`・`examples/`・コード・テストを直す

## 書き方

- 文書は**日本語**。コード中のコメントは英語
- bcuz が出すメッセージは**英語**（`docs/design/decisions.md`）
- 文は短く、1文1つのこと。結論を先に書く
- 用語は `.claude/rules/naming.md` の表に揃える
- 表と箇条書きを使ってよい。ただし、理由は文で書く
- `examples/` の入力は `$ ` で始め、出力はそのまま書く。毎回変わる値（時刻・時間）は、例の中でそう断る
- **文書の相対リンクと `examples/` の内容は、`internal/docs` のテスト（`qsoku unit`）が確かめる。** 文書を動かしたら、リンクを直す
