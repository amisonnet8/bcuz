# ドキュメントの書き方

## 文書の一覧と役割

| 文書 | 役割 | 変えるとき |
|---|---|---|
| `docs/reference/` | **正本**。使い方・出力・メッセージ・終了コード（`cli.md`）と記録の形式（`history.md`） | 仕様を変えるとき。**先に文書、後で実装**。見え方が変わるなら人間の了承が先（`.claude/rules/working-with-human.md` 4章） |
| `docs/design/` | 開発に加わる人向け：`overview.md`（目的・やらないこと）・`decisions.md`（判断と理由）・`limitations.md`（制限と追加の候補） | 判断が変わったとき。候補を採用したら `limitations.md` から消し、`reference/` に書く |
| `docs/examples/` | 実際の入出力。`internal/docs` のテストが実装との一致を確かめる | 挙動を変えたとき（テストが落ちる） |
| `dev/` | 開発のうちうち：`roadmap.md`（段階）、`review/`（了承をもらう資料） | 段階が進んだとき |
| `README.md`・`README_ja.md` | 利用者向けの入口（ヘッダー・バッジ・特徴・入れ方・使い方の要点・`docs/` への案内）。英語が正本で、`docs/` と同じ対の決まり | 使い方が変わったとき。両方を同じ変更に入れる |
| `CLAUDE.md`・`.claude/rules/` | 開発のルール | 気づき・落とし穴が見つかったとき |

- `docs/` から `dev/` を参照しない（`docs/` は利用者にも見せる）
- 進捗・決定・質問は文書ではなく **mtqg** に記録する（`.claude/rules/mtqg-usage.md`）

## 仕様と実装がずれたとき

- **`docs/` が正本。** 実装を `docs/` に合わせる
- `docs/` 自体に誤りや矛盾を見つけたら、黙って実装に合わせない。重要な判断として、推奨案つきで聞く
- 仕様を直すと決まったら、**同じ変更の中で** `reference/`・`examples/`・コード・テストを直す（英語を直して、日本語も同じ変更に入れる）

## 書き方

- **`docs/` は英語が正本**（`X.md`）。日本語は翻訳で、同じ場所に `X_ja.md`（`history.jsonl` は `history_ja.jsonl`）を置く。各ファイルの1行目に、言語の切り替え（英語：`*[日本語](X_ja.md) | **English***`、日本語：`*[English](X.md) | **日本語***`）を置く
- **英語と日本語の対は、同じ構造にする**（見出し・表・箇条書き・コードブロックの数と並び）。コードブロックのうち日本語を含まないもの（メッセージ・使い方・コマンド）は、一字一句同じ。リンクは、同じ言語のファイルを指す。`internal/docs` のテスト（`translations_test.go`）が確かめる
- `docs/` 以外の文書（`dev/`・`.claude/`・`CLAUDE.md`）は**日本語**。コード中のコメントは英語。`README.md` は `docs/` と同じで英語が正本（日本語は `README_ja.md`）。README の最初のコンソール例と使い方の行はテストが照合する（`transcript_unix_test.go`）ので、例を変えるときは `docs/` の例と合わせる
- bcuz が出すメッセージは**英語**（`docs/design/decisions.md`）
- 文は短く、1文1つのこと。結論を先に書く
- 用語は `.claude/rules/naming.md` の表に揃える
- 表と箇条書きを使ってよい。ただし、理由は文で書く
- `examples/` の入力は `$ ` で始め、出力はそのまま書く。毎回変わる値（時刻・時間）は、例の中でそう断る
- **docs の例の値（ハッシュ・出力・件数など）は、推測で書かず、道具で求めるか、実際に動かして確かめて書く**（`.claude/rules/testing.md`「期待値は、テストを書く前に決める」と同じ考え方）。実装より先に docs を書くときも同じ
- **文書の相対リンクと `examples/` の内容は、`internal/docs` のテスト（`qsoku unit`）が確かめる。** 文書を動かしたら、リンクを直す

## `docs/design/`に書く経緯

`docs/design/`には**今の設計**を書く。経緯は、**前のやり方に戻すと、同じ問題がまた起きるもの**だけを書く。それ以外の経緯は、mtqgに記録する（`.claude/rules/mtqg-usage.md`）。

- **書く**：今の設計を選んだ理由で、捨てたやり方に戻すと問題が再び起きるもの。「何を選び、何を捨て、なぜか」を数行で書く。詳しいやり取りは、mtqgのID（`q`・`m`）で指す
  - 例：「XXXアルゴリズムを使う。以前はYYYアルゴリズムを使っていたが、zzzzの問題が起きたため」→ 書く。YYYに戻すと、zzzzがまた起きる
- **書かない**：今の設計の働きに関わらない変更の経緯（名前・表記・置き場所を変えた理由など）、日付ごとの流れ、誰が何を言ったか、途中で直した履歴、todo・bugの進み。これらはmtqgに記録する
  - 例：「ツールの名前はaaaとする。以前はbbbだったが、同じ名前のツールがすでにあったため変えた」→ 書かない。`docs/design/`には「名前はaaa」だけを書く
